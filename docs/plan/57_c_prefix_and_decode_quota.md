# C 第二轮：前缀复用与解码配额

## 基础证据与范围

上一轮 C60 对照成功 1/60，chunk512/1024/2048 + 四轮解码配额分别为 21/24/22。当前不再重复相同配置或完整 HumanEval。独立分支 `step1/c-prefix-scheduling` 基于 `6730362`，保留已有 GPU 实验源树不变。

## 变量与实现

- `r_chunk1024_d1`、`r_chunk2048_d1` 相对对应 d4 只将 `MELLUM_C_DECODE_STEPS` 从四改为一。分段预算、数学路径、专家分组及 KV 单次写入不变。
- `r_prefix_only` 相对未分段参考组合，只打开已有块缓存和参考缓存后缀桥接。不打开 engine chunked prefill，不改变解码配额。
- `r_prefix_chunk1024_d1` 在一轮配额分段基础上打开同样的前缀缓存。profile 可独立关闭缓存以比较增量。
- `MELLUM_REFERENCE_PREFIX` 使 direct KV 保留当前 suffix 的 Q/K/V，由参考 SDPA 读取分页历史；不走旧原生 prefix gather，不改变 RoPE、全局/滑窗绝对位置、BF16 和专家路径。
- 不修改原块管理器。沿用完整块哈希，只有 GPU 计算完成的块才可发布；不缓存模型输出或针对公开提示编写答案。

## 检查与实验

150 项 CPU 检查通过，覆盖前缀完整块发布/共享/释放后复用、绝对位置和缓存布局、调度部分预填充隔离，以及启动参数只开启预期功能。GPU 尚未验证。

每个配置先执行四提示单独生成、四请求混合生成和短提示重复请求。参考来源包括 1023/1025/16384 token 提示。保留与 HF 前八 token 的比较；缓存配置还要求重复阶段确有缓存后缀预填充，且重复输出等于冷启动输出。运行失败、没有真实命中或重复输出不同则停止该配置容量测试，继续其他配置。

随后 C60 使用同样的前 60 条 C 数据，速率 0.3、输出 256、单请求超时 180。GPU0 比较两种 d1；GPU1 在同一源码下复测缓存关闭对照、缓存开启、缓存+分段。C60 通过也不等于 C200 或正式正确性通过。两张卡为独立实验，共享 CPU 资源须披露。

首轮缓存输入复用潜力估计约 37.1%，不是实测加速，不能用来替代本轮命中/完成率。分段路径中 cached_tokens 包含本请求先前 chunk，不能直接把该字段总和称为公共前缀命中量；应区分首次调度的缓存命中与后续 chunk 进度。

## 收敛条件

优先比较同规模负载成功数及失败分布，不把成功请求 p99 当完整 C 成绩。仅对有改善的最终候选做 C200 和完整正确性验收；若仍明显超时，应结合配额、解码批量和预填充重复量定位，不通过提高超时或降低速率掩盖问题。前缀复用与调度的增量收益单独披露，后续按题目最多三个优化点的要求选择交付内容，不靠合并名称跳过消融。
