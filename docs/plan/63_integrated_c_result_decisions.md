# 集成 C60 的分析与后续决策

本轮不修改运行中的 `386d124` 实验工作树。CPU分析工具维护在交付工作树，分析只读取已完成、源码未变化、逐文件哈希一致的结果。运行未完成时不作晋级判断。

## 统一读取

两轮完成后执行交付目录下的 `scripts/analyze_mellum_c_capacity.py --runs <GPU0输出目录> <GPU1输出目录>`。输出独立JSON与Markdown，不覆盖实验原始数据。

核对配置名、请求分母、成功/失败、失败前是否出现HTTP流间隔、最大decode批次、实际prefix命中及取消回收。流间隔不等于token数。取消后若被移除ID再次进入step，视为生命周期异常；没有abort回执则不能证明取消路径执行过。服务端阶段日志含诊断开销，不能充当正式无插桩ABC数据。

## 决策表

| 结果 | 下一步 |
|---|---|
| 任一配置C60全部完成且生成smoke无异常 | 冻结该配置；先C200确认持续容量，再完整正确性与正式ABC/消融 |
| 多配置全部完成 | 结合完整延迟与吞吐选择；短筛查不宣称稳定胜出，最终测试采用同配置 |
| 有失败但明显改善 | 记录改善与未达标；不把成功请求尾延迟作为完整C成绩，不立即投入完整HumanEval |
| 三配置均失败 | 保留已验证decode与取消修复，定位剩余服务开销；不再重复仅改prefix/chunk的小步扫描 |
| 生成或生命周期异常 | 单独隔离集成问题；已有子方案的正确性不能覆盖组合 |

场景C要求200请求、单卡rate0.3、输出256、请求超时180秒保持不变。不能以放宽超时、降低负载、取消请求冒充成功等手段解决容量问题。C60全完成只是进入完整验证的条件。

## 正式收敛

单卡方案优先，不展开P/D。候选冻结后，主版本与消融最后一行必须采用相同代码、开关、槽数及服务参数。完整正确性包括200提示前64token位置一致率、长上下文单列、BF16 HumanEval与HF差距；不因局部计算相同免除最终组合验收。MTP关闭，双卡模型并行未使用。

预测收益与实测收益分别记录；没有事前数字预测的地方保留空白。尚未完成的C200、ABC、组合HumanEval与正式消融数据保持待测。
