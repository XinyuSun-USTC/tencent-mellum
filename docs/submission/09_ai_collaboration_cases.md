# AI协作审查与修正记录

本页为根目录一页[AI使用说明](../../AI_USAGE.md)的答辩备查材料。内容依据会话、代码及实验记录归纳，不冒充逐字引文，不补造精确讨论时刻或个人工时。本文中的“本人”指候选人；AI承担辅助实现和分析，不代替本人作最终决策。

## 1. 明确任务与环境边界

最初需要同时厘清Step0与出题方baseline、冻结环境与参考环境之间的关系。本人明确首要任务是尽快实现自己的正确适配，无需刻意复刻出题方源码，同时要求为后续优化保留扩展性。对于HF参考，进一步澄清推理环境必须冻结，而独立验证环境可以安装合适的Transformers。

这一判断促成了冻结推理依赖与独立HF参考并存的方案，避免为获得参考而修改待测环境。环境导入、真实checkpoint运行及生成一致性分别验证，不以安装成功代替参考可用。

## 2. 纠正正确性诊断的投入方式

早期AI采用逐层、同前缀、固定输入重放，确实帮助定位专家、投影、RoPE、注意力和采样分流问题。但多轮实验后，中间张量或logits精确逐步成为事实上的额外目标，耗时超过适配阶段应有范围。

本人多次要求回到题目门槛，指出自回归生成会放大小数值差异，并要求引入HumanEval功能评估、停止对每项小优化重复完整验证。协作方式随后调整为局部诊断、有界筛查及最终集中验收。需要同时保留反向约束：HumanEval可接受不代表逐token门槛自动通过。后期激进配置仅62.85%位置一致率，说明两项评价不可相互替代。该修正是控制验证范围，而非放宽题目要求。

证据：[Step0定位总结](../../report/validation/39_step0_summary.md)、[功能评估](../../report/performance/22_fused_moe_humaneval.md)、[激进组合复核](../../report/performance/36_combined_full_abc.md)。

## 3. 扩大调研与评测覆盖

本人指出仅在当前ATOM中自行寻找方案可能限制优化空间，要求阅读框架内其他模型及上游ATOM、vLLM等实现。相关研究扩大了原生专家、注意力、graph和缓存的候选范围，但没有升级冻结依赖或更换交付引擎。

本人也要求扩大profiling与测试规模，并组织两卡独立批量实验以减少人工介入。索引专家GEMV局部约4.892倍，而前64token一致率仅78.23%；prefill逐元素合并没有实质收益。这些反例帮助将局部性能、实现语义和最终验收分开处理，停止无效候选晋级。

证据：[实现来源调研](../../report/research/05_optimization_implementation_sources.md)、[索引专家结果](../../report/performance/15_indexed_decode_d200.md)、[逐元素合并](../../report/performance/18_prefill_elementwise.md)。

## 4. 修正主版本与消融的证据错配

旧材料曾将正确性通过的保守配置和性能较好的激进配置纳入同一主版本叙述；消融最后一行也没有对应实际默认入口。本人明确指出，Step0＋123应当等于交付主版本，不能只在文档中添加限制说明而不修复配置关系。

最终建立 `mellum_delivery_matrix.py` 共用行定义，启动入口、完整正确性和ABC均选择同一行，默认step0123等于累计消融末行。历史结果继续保留原配置身份。Step0明确为最终源码关闭优化后的重跑，不改写为历史提交逐字节复现。此时入口和矩阵关系已在代码中统一，但本轮完整实验尚未完成，不能写成最终性能或正确性已通过。

证据：[最终实验方案](../plan/65_final_delivery_matrix.md)、实现提交 `e1f3e22`、入口修复 `6f02551` 和 `4fa8ddb`。

## 5. 将重点转向场景C及统计口径

此前对局部kernel和外围开销投入较多，而参考正确组合仍有严重C超时。本人重新引用题面关于decode stall、共享前缀和chunked prefill的说明，要求优先解决场景负载问题；在双卡P/D与单卡方案之间，明确优先延续已有单卡实现。

后续实验覆盖分段prefill、decode配额、前缀复用、隔离decode及客户端断连。最佳集成C60完成43/60，仍不足以证明完整C可承受。新增profile表明全局SDPA、专家和长prefill均有明显开销，不支持只靠调度参数解决全部缺口。

本人进一步质疑180秒的性质，以及超时后分位数如何计算。源码核验确认180秒是命令指定的单请求超时，EvalScope分位数仅覆盖成功请求。AI此前直接将“不全完成”等同于题面明确的C不通过，表述过强；最终报告改为同时披露成功样本分位数、完成数与失败数，既不自行补造判罚规则，也不借较低的条件分位数宣称全负载达标。

证据：[C60集成结果](../../report/performance/44_integrated_single_gpu_c_screen.md)、[最新profile](../../report/performance/45_integrated_c_bottleneck_profile.md)。

## 6. 处理AI生成工具的实际故障

工具实现中出现过set序列化失败、AITER导入路径错误、HF构造参数与版本不匹配等问题。本人通过实际终端返回异常，要求依据当前环境源码定位，而不是仅凭生成代码或预期API判断可运行。

最终累计实验又暴露smoke端口复用与缺失摘要处理不当。日志证实第一行服务已通过，第二行因端口仍占用而退出。修复采用新工作树，为每行分配独立端口、直接替换启动进程、核对端口释放并保存异常摘要；原失败结果保留。模型计算未因测试工具故障而被误判，CPU检查也没有被表述为GPU验收。

## 7. 最终协作边界

本人负责题意、优先级、预算和最终审查；AI负责辅助实现、检索、脚本与分析。运行编号、源码/产物哈希、原始trace和失败结果用于约束结论。没有测量的数据保留空白，没有事前数值预测的项目不作事后补写，上游组件不表述为原创内核。

本次文档修订不修改运行中的实验代码。最终消融与完整验收仍以当前冻结配置的实际结果为准，AI不能替代裁判测量或最终责任承担。

## 基线范围的最终修正

候选人进一步指出，单槽Step0完整性能补测耗时较长，而已有完整r32数据可用。核对profile后确认r32到专家group4仅增加decode_expert_group_size=4。因此将兼容批处理、逐请求投影、共享routing纳入Step0，优化①仅计group4；旧单槽记录保留为初始适配参考。代码、入口、矩阵和文档在独立交付树同步更新，历史结果不改名、不隐去测量版本。
