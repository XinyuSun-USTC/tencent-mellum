# C 场景分段预填充与解码配额筛查

运行 `mellum_c_chunk_screen/20261116T204832193530Z`、`20261116T204837799320Z` 分别在两张卡上独立测试，两卡共享主机资源，不构成双卡模型推理。112 个产物哈希均核验通过，运行期间源码未变。比较使用相同 C 数据前 60 条，速率 0.3 请求/秒，输出 256，单请求超时 180 秒，到达跨度约 198.34 秒。

四个配置均完成了四提示单独生成和四请求混合生成，包含 1023、1025 与 16384 token 输入；各阶段前八输出 token 与已有 HF 参考完全一致。分段配置均观测到缓存后缀预填充，容量阶段实际预填充 token 总数上限分别为 512、1024、2048。这是小样本运行和语义筛查，不是完整 HumanEval 或 developer200 验收。

分段提高了成功数，但所有配置仍有失败，因此不能将成功请求的 TTFT/TPOT 分位数当作完整 C 成绩。HTTP 流间隔不是精确 token 计数；没有间隔不证明引擎没有计算。批次记录缺少时间戳，不据此宣称测得 prefill stall 的具体持续时间。

## 判断与下一步

分段与解码配额这一组合策略有积极信号，但未解决持续容量。1024 的成功数最多，2048 的成功请求首 token 等待更短、实际解码批量更大，呈现准入与解码服务之间的权衡。尚不能从一次样本判定哪个参数全局最优，也不能把改善全部归因于分段大小，因为本轮分段和解码配额同时启用。

下一轮优先比较较小的解码配额（如一轮），以检查四轮配额是否抑制新请求完成预填充；不重复本轮候选的完整 HumanEval。另评估公共前缀缓存，保留相同外部负载。CPU tokenizer 分析发现 200 条 C 输入共享 3820 token 前缀，16-token 块粒度可复用 238 块，理想减少 757792/2039880=37.1489% 输入 token。该计算不考虑命中时机、驱逐、部分块及缓存管理开销，不是命中率或加速比实测，也不保证足以解决 C。

前缀缓存应在独立工作树接入已实现的参考缓存后缀路径，先检查命中前后的输出、分页与长输入语义。不得复用生成答案或按公开请求硬编码。若沿此路线继续，前缀缓存与调度的增量收益必须分别披露，不能以“同为 C 优化”为由省略消融。

归档：`artifacts/submission/c_chunk512_1024_screen/`、`c_control_2048_screen/`、`c_chunk_analysis/`。已验收参考组合仍是正确性候选，而非 C 达标版本；新分段候选尚不晋级。
