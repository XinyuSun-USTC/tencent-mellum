# C 首次预填充等待与公共前缀计量

## 方法

新增 CPU 工具 `scripts/analyze_mellum_c_prefix_log.py`，从到达日志和预填充调度日志配对同一请求。只统计输入 4000–16384 token 的请求，以排除九 token 的服务预热；本轮各日志均识别到 60 条 C 请求。时间戳仅精确到秒，测量为到达到首次预填充被调度的等待，不是 GPU 时间，也不是 TTFT。

首次调度的 cached_tokens 用于识别已有前缀复用；后续 chunk 的 cached_tokens 是本请求的已计算进度，不能累加为公共前缀命中量。工具保留未观察到首次调度的请求，不把它们当作零等待加入中位数。输出包含原日志哈希。三项 CPU 测试覆盖分段/前缀区分、未准入请求、跨午夜和非法元数据。

## 旧 C60 日志结果

| 配置 | 到达数 | 观察到首次预填充 | 已准入请求等待中位数 | 最大等待 | 首次前缀复用 |
|---|---:|---:|---:|---:|---:|
| 未分段参考组合 | 60 | 60 | 1 秒 | 72 秒 | 0 |
| chunk1024 + 四轮解码 | 60 | 47 | 115 秒 | 233 秒 | 0 |

## 对实验选择的意义

结合原 C60 成功数 1/24/22，分段与四轮配额改善了部分已运行请求，却显著推迟了新请求首次预填充；不能只看成功请求 TPOT 就宣称调度已改善所有请求。等待中位数只覆盖日志内观察到调度的请求，其余请求缺少可观测等待终点，不能静默剔除后解释为全体中位数。

当前正在执行的一轮配额实验用于检查这一准入与解码服务的权衡；公共前缀缓存则减少需要计算的预填充量。若二者仍不能承受负载，应进一步检查实际算时与超时取消链路。超过 180 秒的首次调度等待提示超时请求可能继续消耗资源，但该日志分析没有逐一关联客户端完成事件，不能据此宣称已量化取消缺口造成的全部损失。

工具本身不改变服务器、到达率或超时，不占 GPU，也不作为候选正确性或性能通过结论。
