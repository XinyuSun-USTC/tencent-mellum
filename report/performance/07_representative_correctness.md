# 07 代表性正确性评测：开发200与HumanEval试跑

CK候选保留为**可选优化方案**，默认仍关闭；不再以0.57%张量差异或三条边界样本直接否决。开发200按token位置口径93.11%达到90%；完整序列匹配87.5%作为补充报告，不擅自将其加为题目硬门槛。集合身份和正式一致比例口径仍待出题方确认，不能宣称正式通过。

HumanEval工具链及4题完整生成/功能评分打通，双方75%、差0个百分点；不是164题正式HumanEval结论。下一阶段不自动启动全量长任务，不继续为bitwise精确耗费实验；如进一步筛候选，直接复用真实QKV做局部对照，再以题目生成指标验收。

## 开发200结果

复用已验HF5.10.1输出，仅跑候选，正常greedy每条64token、ignore_eos=False、权重审计5631/5631无异常，实际SWA优化=1。

| 分组 | 提示词数 | token位置匹配 | 完整64token序列匹配 |
| --- | --- | --- | --- |
| 全部 | 200 | 11918/12800 = 93.1094% | 175/200 = 87.5% |
| ≥1024，激活优化 | 32 | 1166/2048 = 56.9336% | 7/32 = 21.875% |
| <1024，不激活优化 | 168 | 10752/10752 = 100% | 168/168 = 100% |

按题目“逐token一致比例”的位置解读，本地开发指标达到90%，而不是此前三条合成样本暗示的整体21%。若裁判采用整序列比例则结果不同，因此如实列出两项，不能擅自增加或放宽标准。200由164 HumanEval+36 scenario A构成，32个激活样本全为scenario A；总体分数依赖长短输入混合比例，不外推公开/隐藏集。

168个不激活样本全精确，说明影响确实局限于候选作用范围。25条激活样本序列不同，表明长输入的生成敏感性真实存在，不因总体93.1%而消失。保持这个候选用于消融合理；是否最终选择应结合正式口径、代表性负载、其它候选收益与准确性，而非以“使用AITER”或“张量误差小”直接保证。

双方pass@1=75%，差0个百分点，无逐题得失变化。第10题失败是预算/未完成输出，不能解释成算法代码错误，也不应从分母去掉。4题规模和截断不支持全164的≤2个百分点验收结论。

所有HumanEval完整协议输入73–456token，均不启用本优化；即使输出跨越1024，decode路径仍未改。因此这些分数用于补齐功能评测，对长输入候选的约束力有限。没必要为证明本prefill开关而立即耗时数小时重复全量Thinking生成；完整HumanEval可在最终候选/评测协议固定后单独补齐。

## 下一步取舍

1. 将CK路线从“因三条样本分叉而不采纳”更新为“有明显TTFT收益、开发200位置口径达标的实验候选”，保留独立开关和风险说明，不自动改默认后端。
2. 先明确公开集/一致比例口径，继续分层报告长输入结果；没有额外信息时按逐token位置为主、整序列为辅，不伪称官方通过。
3. 暂不跑全164 Thinking长任务或重复ABBA。若筛选更兼容窗口实现，先复用1K/4K真实QKV做廉价数值/耗时筛选，再对同开发集合比较，不追求额外bitwise硬门槛。
4. 完整HumanEval需要固定足够预算和代码提取协议。可以后续只提高截断题预算或另建明确的non-thinking协议，但应单独报告，不能把pilot75%与其它协议混成同口径参考值。
